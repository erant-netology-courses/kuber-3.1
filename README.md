# kuber-3.1

Дано:

> 1. Необходимо упаковать приложение в чарт для деплоя в разные окружения. 
> 2. База данных должна быть отказоустойчивой. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
> 3. Кеш должен быть отказоустойчивый. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
> 4. Фронтенд обрабатывает внешние запросы быстро, отдавая статику. Потребляет не более 50 МБ ОЗУ на каждый экземпляр, 0.2 ядра. 5 копий. 
> 5. Бекенд потребляет 600 МБ ОЗУ и по 1 ядру на копию. 10 копий.

----

### Правила приёма работы

1. Домашняя работа оформляется в своем Git-репозитории в файле README.md. Выполненное домашнее задание пришлите ссылкой на .md-файл в вашем репозитории.
2. Сначала сделайте расчёт всех необходимых ресурсов.
3. Затем прикиньте количество рабочих нод, которые справятся с такой нагрузкой.
4. Добавьте к полученным цифрам запас, который учитывает выход из строя как минимум одной ноды. 
5. Добавьте служебные ресурсы к нодам. Помните, что для разных типов нод требовния к ресурсам разные. 
6. В результате должно быть указано количество нод и их параметры.

## 2. Общий расчет всех необходимых ресурсов

1. БД - 12 ГБ, 3 ядра
1. Кэш - 12 ГБ, 3 ядра
1. Фронт - 0.25 ГБ, 1 ядро
1. Бек - 6 ГБ, 10 ядер

Итого: 30.25 ГБ, 17 ядер

## 3. Количество рабочих нод

Нужно минимум 3 ноды для отказоустойчивости (по 3 копии БД и Кэша). Минимальные характеристики ноды в таком случае: 
```
30.25 / 3 = 10 ГБ RAM
17 / 3 = 6 ядер
```
3 ноды 8vCPU/16GB

## 4. Выход из строя 1 ноды (или более)

Базово в данном сетапе 1 нода - 33% от мощности. 
Рассчет падения нод:
```
Базовый минимум (30.25 ГБ, 17 ядер) <= (N - M) * размер_ноды
где N - общее количество нод, M - количество упавших нод
```
Т.е. в нашей ситуации либо надо 4 ноды 8vCPU/16GB, либо 3 ноды 12vCPU/32GB

## 5. Служебные и системные траты

Формула ресурсов для k8s:
```
Allocatable = Capacity − kubeReserved − systemReserved − evictionThreshold
```
По факту раскладывается в % от ресурсов разных размеров.

У 4 нод по 8vCPU/16GB доступно:
CPU: ~7.9 ядра
RAM: ~13GB

У 3 нод по 12vCPU/32GB доступно:
CPU: ~11.9 ядра
RAM: ~28GB

## 6. Результат

4 x 8vCPU/16GB по факту `4 x 7.9vCPU/13GB = 31.6vCPU/52GB`

Падает 1 нода: `31.6CPU/52GB - 7.9CPU/13GB = 23.7vCPU/39GB` выдержит падение 1 ноды.

----
3 x 12vCPU/32GB по факту `3 x 11.9vCPU/28GB = 35.7vCPU/84GB`

Падает 1 нода: `35.7vCPU/84GB - 11.9vCPU/28GB = 23.8vCPU/56GB` выдержит падение 1 ноды.

----
При 3 нодах больше запас по оперативке и используются 3 ноды - легче обслуживать, но дороже стоят ноды и падение машины отнимает 33% ресурсов. 

При 4 нодах меньше запас и используеются 4 ноды - более надежно (упала одна, есть еще 3), падение отнимает меньше (25%) ресурсов. И чуть больше мониторить. 

С учетом всего я бы выбрал 4 ноды:
1. Выше отказоустойчивость
2. Более равномерное распределение
3. Скорее всего будет дешевле
